# حماية قاعدة بيانات الإنتاج

التحديث الحالي: الترحيل `20261015215545_require_staff_and_reduce_privileges.sql` يلغي خدمات الزائر العامة. كل خدمات البيانات والرفع تحتاج حساب موظف نشط وجلسة قائمة في Auth. المشاهد يقرأ فقط. دوال الاستعلام تعمل الآن بصلاحيات المستدعي وRLS، والدوال القديمة غير المستخدمة غير متاحة للعملاء. حاجز PostgREST الخاص يرفض الطلب قبل تنفيذه، بينما Storage محمي بسياسة RLS مستقلة. كابتشا تسجيل الدخول يتحقق منه Supabase Auth نفسه.

استخدم `verify-staff-access.sql` للتحقق من الحالة الحالية داخل معاملة ملغاة. الاختبار السابق أدناه تاريخي، ولا يناسب سياسة منع إدخال الزوار الحالية. إعادة تطبيق الترحيل الأول وحده ستعيد السياسات القديمة؛ يجب تطبيق الترحيلات بالترتيب.

طُبق الترحيل `supabase/migrations/20261015212929_production_access_and_atomic_codes.sql` عبر Supabase Management API في 16 أكتوبر 2026 بتوقيت القاهرة.

- الجدول الفعلي للمركبات orders، وcode نصي، ومعرف السجل uuid، والتواريخ bigint بالميلي ثانية.
- الدالة assign_vehicle_code تعمل بصلاحيات المستدعي وتحتاج موظفًا نشطًا ADMIN أو SUPER. تعتمد على قفل السجل وسجل حجوزات خاص ذي مفتاح أساسي فريد، وتحترم RLS.
- يوجد تعارض تاريخي للكود 1960 على سجلين. حُجز الكود لمنع إعادة استخدامه ولم يُحذف أو يُعد ترقيم أي سجل مواطن. يُنشأ الفهرس الفريد المباشر على orders تلقائيًا عند زوال التعارض التاريخي؛ حجز الأكواد الجديدة محمي الآن بقيد الجدول الخاص.
- production-hardening.sql يقيد الكتابة ويمنع تزوير هوية سجل العمليات، ويصلح رجوع NULL من دوال الأدوار، ويحمي تخزين الصور. يُسمح للزائر بإنشاء طلب أو شكوى بحالة pending فقط، ولا يُسمح له بالتعديل أو الحذف أو التكويد.
- verify-production.sql للاختبارات المعزولة داخل معاملة تُلغى. يحتاج إعداد app.verify_super وapp.verify_viewer بمعرفي مستخدمين فعليين داخل المعاملة. لا يتضمن كلمات مرور أو توكينات.

نجحت اختبارات SQL الأحد عشر واختبار طلبين متزامنين للكود نفسه، وأزيلت جميع بيانات الاختبار. أي تغيير لاحق يجب تسجيله بترحيل جديد وفحصه قبل تطبيقه.
